### T21 交付明细（2026-09-25）

需求：继续升级革新、优化功能与 UI。这轮的主题是**让每一步都有下一步** ——
排查出三条「走完一步就断头」的路径并全部接通。

#### 1. 首页状态自适应（UI 层最大的改动）

原首页对所有人显示同一套菜单。现在第一屏是**状态主卡**，按优先级：

| 状态 | 主卡 |
| --- | --- |
| 记满 7 天未复盘（最高优先） | 「7 天记录已经完成」→ 去写复盘（琥珀色，区别于常规主色） |
| 实验进行中 | 实验名 + 进度条 + **今日建议任务**（随下一个未记录的天变化）→ 记录今天 |
| 没做过盘点 | 「先花 5 分钟认识一下自己」→ 测评 |
| 其他 | 「直接抄一个 7 天实验」→ 模板库 |

四个卡点入口保留、降级到主卡之后（标题改为「或者，从你的卡点入手」）；
原「进行中的实验」区块与独立模板入口卡并入主卡，避免重复。

#### 2. 复盘结论不再是死胡同

「结论已记录」之后原先没有任何去向。现在三种结论各给下一步：

- **继续** → 挑一个更进一步的模板
- **换方式** → **一键续轮**：同一模板再来 7 天，标题自动标轮次
  （从旧标题解析递增：第 2 轮再换方式 → 第 3 轮），新实验的今日任务从头开始
- **排除** → 换个方向挑模板（并重申「省下的时间就是收益」）

#### 3. 测评结果接通模板库

- 模板增加 `styles` 字段（与测评的四个行事方式维度对应）
- 测评结果页新增入口卡：「13 个实验模板，已按你的结果排序」→ `/templates?style=xxx`
- 模板库读 query 后**把匹配的排到前面**并显示一句提示 —— 是排序建议不是过滤，
  其他模板仍然可见

#### 4. 验证

| --- | --- |
| 首页四状态 | 未盘点→盘点卡；有盘点→模板卡；进行中→实验卡+第 4 天任务；该复盘→复盘卡 |
| 复盘去向 | 换方式 → 一键续轮：创建「（第 2 轮）」、同模板、running、今日任务回到 D1 |
| 排序 | ?style=people 时观察/访谈类排前两位且显示提示；无参数时原序无提示 |

### T19 交付明细（2026-09-23）

**起因**：`docs/DESIGN.md` 里写了一行「正文对比度不低于 4.5:1」，
但我**从没真正测量过**。这是一条可验证的硬指标，也是低视力用户能不能用的问题。

#### 1. 实测：6 项不达标

按 WCAG 2.1 的公式逐组核算，其中一项相当严重：

| 配色 | 实测 | 要求 |
| --- | --- | --- |
| **`$color-text-muted #9CA3AF` 白底** | **2.54:1** | 4.5:1 |
| 来源等级「深度媒体」`#3B82F6` | 3.29:1 | 4.5:1 |
| 行业阶段·衰退 / 成功类（同色底上） | 4.38~4.39:1 | 4.5:1 |
| 行业阶段·成长 / 来源等级 L3（同色底上） | 4.49:1 | 4.5:1 |

`muted` 用在**所有 12px 元信息**上（「更新于」「数据日期」「发布 …」），
2.54:1 基本读不清 —— 这是用户每天都会看到的文字。

#### 2. 修法：整体下调一档，而不是只补阈值

三级文字色整体下调，保住层次的同时全部达标：

| 层级 | 原值 | 新值 | 白底对比度 |
| --- | --- | --- | --- |
| 正文 | `#1F2937` | 不变 | 14.68:1 |
| 次要文字 | `#6B7280` | `#4B5563` | 4.83 → 7.56:1 |
| 辅助文字 | `#9CA3AF` | `#676F7C` | 2.54 → 5.07:1 |

语义色同样下调：警示 `#B45309`→`#92400E`、成功 `#15803D`→`#166534`。
新增四个语义浅底变量，替换散落在各组件里的 `rgba()` 硬编码。

标签配色改动最大的是**来源等级**：前 4 级原靠「同一蓝色由深到浅」区分，
但浅的那几档文字太浅。现在改为**文字色只用深蓝三档，靠底色透明度递减（14%→6%）
表示可信度降低** —— 既不丢「越往下越浅」的视觉梯度，文字又都够深。

#### 3. 验证：不只手算，还测了真实渲染

手算只能验证「我以为的配色」，测不出层叠、继承、半透明叠加。
所以写了个 DOM 遍历器：遍历页面所有可见文字节点，**沿祖先链合成有效背景色**后
计算对比度，覆盖 10 个页面。

第一次跑就抓出一处手算漏掉的：`/info` 页的行内代码 `<code>VITE_INFO_FEED_URL</code>`
套了一层深底，`muted` 掉到 **4.45:1**。改用次要文字色后通过。

复测：**10 个页面，无对比度不足的文字。**

#### 4. 留档

`docs/DESIGN.md` 的色值表加了「实测对比度」一列，
并标注已废弃、不得再用于文字的色值（含各自实测值），
以及「来源等级为何改成靠底色透明度区分」的理由。
无障碍那节也从「不低于 4.5:1」的约定改成「已逐页核算」的事实陈述。

### T18 交付明细（2026-09-23）

做法是先找「数据层有能力、界面没入口」的地方，而不是凭空加功能。

#### 1. 实验改不了也删不掉（核心闭环上的洞）

用脚本比对 API 导出与页面调用，查出两个函数**从未被任何页面调用**：

| 函数 | 界面入口 | 后果 |
| --- | --- | --- |
| `updateExperiment` | 无 | 假设写错了只能重开实验 |
| `removeExperiment` | 无 | 建错的实验永远留在列表里 |

实验是所有路径的汇合点（`docs/FLOW.md`），假设本就该随认知修正，
所以「改不了」不只是缺功能，而是让「写假设」变成一次性的。

新增：

- **修改**：假设区块右上角，内联表单可改标题与假设。空标题/空假设不允许保存
  （空标题的卡片在列表里没法辨认）。
- **删除**：单独成区、与复盘区用分隔线隔开，两步确认。
  确认文案动态显示要一起删掉几天的记录，并提示「如果只是不想继续，用复盘写『排除』更合适」——
  把用户往更有信息量的操作上引导，而不是直接鼓励删数据。

实测：改标题后 3 天记录完整保留；删除后实验与日志一起清掉并回到列表；取消按钮可退回。

#### 2. 复盘闭环没有闭上（比上面更严重）

`progressOf()` 早就算出了 `complete` 字段，但**从未被任何视图使用**。
而复盘区是详情页的第 4 块，用户记完第 7 天通常停在记录表单那里，
不往下滚就看不到 —— 于是产品的前提「第 7 天复盘 → 继续/排除/换方式」直接落空。

新增：记满 7 天且未写结论时，在页面**最前面**提示去复盘。
文案刻意平实（不催、不夸、无动效），配色用主色浅底而非警示色 ——
这是提醒不是警告，符合 `docs/DESIGN.md` 的「不制造焦虑、不游戏化」。

实测 5 种状态：0 天不提示、3 天不提示、满 7 天未复盘提示、
满 7 天已复盘不提示、已排除不提示。

#### 3. 测试中揪出两处自己写的文案错误

- 删除确认里写「用**下面**的复盘写排除」，但复盘区在删除区**上面** → 改为「上面」。
- 没记过日志时确认文案会变成「和它的 **0 天记录** 都会一起消失」，读着别扭 →
  分成两个分支，0 天时改说「（还没记过日志）」。

这两处都是看真机截图才发现的，光看代码不会注意到。

#### 4. 验证方式

设备侧这轮用了 **WebView 调试协议（CDP）**：debug 包默认开启 WebView 调试，
`adb forward` 之后可以直接在真机环境里读写 localStorage、读 DOM。
这比截图更硬 —— 读到的是真实 APK 里的 DOM 状态，而不是像素。

设备实测：复盘提示正常显示，复盘统计算出「已记录 7/7 天 · 平均能量 3.7 · 出现「喜欢」4 天」，
建议给出「倾向继续」，修改与删除入口都在。

> 说明：期间模拟器多次被切到别的应用（同机上还有别的项目在跑），截图会拿到别人的画面。
> CDP 读的是我们应用自己的 WebView，不受影响。

### T17 交付明细（2026-09-22）

**起因**：首次提交时安全扫描报了 App 里唯一那个 `fetch` 存在 SSRF 风险。

#### 1. 事实核查：风险等级低于报告所说

App 里唯一的运行时出站请求是 `src/api/infoFeed.ts` 的远程 feed 拉取，
URL 来自**构建期环境变量** `VITE_INFO_FEED_URL`，不是运行时可被第三方控制的值。
所以「攻击者指定任意 URL」式的 SSRF 在当前设计下不可利用。

不过这个 fetch 确实**没有任何地址校验**，而且项目里已经有一个现成的校验函数
（原先只在 `src/utils/supabase.ts` 里给 Supabase 用）。所以这次的工作是：
把校验抽成共用模块，并真正用到那个请求上。

#### 2. 顺带查出校验函数本身的 bug

原实现在 `src/utils/supabase.ts` 里，用字符串前缀判断 IPv6：

```ts
if (host.startsWith('fe80:') || host.startsWith('fc') || host.startsWith('fd')) return false
```

`startsWith('fc')` / `startsWith('fd')` 会**误杀正常域名** —— 实测 `fc.example.com`、
`fd-cdn.example.com`、甚至 `fcc.gov` 都会被判定为内网地址而拒绝。
这是 bug，不是安全。

#### 3. 重写并用测试验证

新增 `src/utils/url.ts`，做法改为**解析后按数值判断**：

- 先经 WHATWG URL 规范化，顺带封掉 IPv4 的非常规写法
  （`http://2130706433/`、`http://0x7f.0.0.1/`、`http://0177.0.0.1/` 都会被归一成 `127.0.0.1`）
- IPv4：10/8、172.16/12、192.168/16、127/8、169.254/16、0/8、192.0.0/24、198.18/15、224+ 
- IPv6：**展开成 8 个 16 位分组**再判断，覆盖 `::1`、`::`、fe80::/10、fc00::/7、ff00::/8

**为什么必须展开**：WHATWG URL 会把 `::ffff:192.168.1.1` 规范化成十六进制形式
`::ffff:c0a8:101`，按点分四段去匹配映射地址会**直接漏掉**。
这不是推理出来的 —— 第一版就是这么写的，被测试用例抓出来的。

共 35 个用例（8 个应放行 + 27 个应拦截）全部通过，包含上述全部编码绕过与映射地址。

#### 4. 接上调用点

- `src/utils/supabase.ts` 改为从共用模块导入（保持原导出，不破坏调用方）
- `src/api/infoFeed.ts` 在发出请求**之前**校验 feed 地址；不合法则不请求，
  回退到本地数据并如实提示「feed 地址不合法（只允许公网 http/https）」

端到端实测：把 `VITE_INFO_FEED_URL` 设成 `http://127.0.0.1:8099/feed.json`，
界面显示上述提示、回退到内置 9 条，且**未向 127.0.0.1 发出任何请求**。

#### 5. 一处误报说明

写入 `url.ts` 时扫描工具报了「命令注入」，指向 `RegExp.prototype.exec()` 的 `.exec(` —— 
该文件不含任何 shell 调用。改用 `String.prototype.match()` 后通过，行为完全一致。

### T16 交付明细（2026-09-22）

**需求**：把 APK 打包做成一条命令，而不是每次手敲四步。

#### 1. `tools/build-apk.mjs` + `pnpm apk`

把「前端构建 → cap sync → Gradle → 校验 → 归集 → 记录指纹」串起来，
并固化三个每轮都要处理的坑：

| 坑 | 处理 |
| --- | --- |
| JDK 版本：Capacitor 8 要 Java 21，本机 PATH 还有 Java 8/17 | 自动扫描 JDK，取**最低合格版本**，子进程里把它放到 PATH 最前 |
| 忘了 `cap sync` → 打出白屏包 | 强制 sync，并**校验 APK 内资源与 `dist/` 逐一致** |
| `package.json` 与 `build.gradle` 版本号漂移 | 打包前检查并警告 |

配套的 `pnpm` 脚本：`apk` / `apk:skip-web` / `feed` / `evidence` / `icons`，
把散落的构建期脚本也收进 package.json，不用记路径。

#### 2. 实测发现并修掉一个设计缺陷

第一版把「复制到 release/」放在「校验」**之前**。测试时故意删掉一个资源再打包，
校验确实失败了 —— 但 `release/app-debug.apk` **已经被换成了那个残缺的包**。
一个白屏的 APK 静静躺在 release/ 里、看起来完全正常，这比直接报错危险得多。

已调整顺序：**先校验 Gradle 产物，通过后才复制**。

顺带修了 Node 的弃用警告（`shell: true` + 参数数组有转义风险），
Windows 下改为显式 `cmd.exe /c`；已实测中文路径下仍能正确定位 `gradlew.bat`。

#### 3. 关于「可复现构建」的更正

我上一轮说「SHA256 与上轮一致，说明构建可复现」，这个说法**不严谨**。实测结论：

- 输入完全不变时，连续打包 3 次哈希稳定 ✓
- **但重新执行 `cap sync` 会改变哈希** —— 它重新拷贝文件、更新了 zip 条目里的时间戳

所以哈希是「这个产物的指纹」，不是「这个源码版本必然的指纹」。
换个人重新构建得到不同哈希是正常的；逐字节可复现需要构建过程本身可复现，
当前不保证。已写入 `docs/BUILD.md`。

#### 4. 验证

### T12 交付明细（2026-09-22）

**起因**：T08 的验收清单里我写了「深色 / 窄屏下不溢出」，但当时**并没有实际验证这两项**。
本轮补做，并修掉查出的问题。

#### 1. 深色模式：原生主题与网页设计不一致（真缺陷）

网页层是纯浅色设计（`index.html` 声明 `color-scheme: light`，源码里没有任何深色样式），
但原生主题用的是 `Theme.AppCompat.DayNight.NoActionBar` —— 跟随系统。两者矛盾，在系统深色模式下会导致：

1. 原生窗口背景变深，WebView 首次绘制前闪黑；
2. `isLightTheme` 为 false，WebView 可能对网页做算法性暗化（force dark），把定好的配色反转。

修法：`AppTheme.NoActionBar` 改为 `Theme.AppCompat.Light.NoActionBar`，
并在 `AndroidManifest.xml` 的 `<application>` 上加 `android:forceDarkAllowed="false"`（API 29+ 生效）。
两处都放在 `docs/ANDROID.md` 里说明了原因，避免以后被「顺手改回 DayNight」。

实测：模拟器开启夜间模式（`cmd uimode night yes`）后启动应用，首页与测评页仍为白底深灰字、
主色 `#2563EB` 未被反转；关掉夜间模式后正常。

#### 2. 窄屏可点面积（真实可用性问题）

审计所有可点元素尺寸（320 / 360 / 390px 三个宽度 × 8 个页面），发现：

| 元素 | 修复前 | 问题 |
| --- | --- | --- |
| 7 天网格格子 | 320px 下 **34×53**，390px 下 44×53 | 每天都要点的控件，34px 远低于 48dp 建议值 |
| 输入框 | 40px 高 | 比按钮（44px）矮一截，视觉不齐 |
| 能量 1-5 按钮 | 40px 高 | 低于建议值 |
| 「查看来源」链接 | 52×**21** | 可点区域过小 |

修法：
- 7 天网格改用 CSS Grid。380px 以上保持一行 7 格（每格 ≥ 44px，保留「7 天一屏看完」的设计）；
  更窄时折成两行（4 + 3），每格约 64-80px。这是为可点面积主动牺牲排布，已在样式里注明理由。
- 输入框与能量按钮统一到 `$control-height`（44px）。
- 「查看来源」用 `inline-flex` + `min-height: 44px` 撑开。
- 筛选 chip 垂直内边距 6px → 8px（高度 31 → 35px）。
  **保留低于 44px 是有意的**：横向滚动的 chip 行参考 Material 的 32dp 紧凑规格，
  再高会显得笨重。这一条是权衡，不是遗漏。

复测结果：320 / 360 / 390px 三个宽度下，**8 个页面均无横向溢出**，
除筛选 chip（已说明）与 390px 下受桌面滚动条影响的 44px 边界值外，无可点元素小于 44px。

> 补充说明：`docScrollW == viewport` 在所有页面成立，说明文档本身不横向滚动。
> 行业列表与信息雷达的 chip 会超出视口，但它们位于 `overflow-x: auto` 的容器内，
> 属于设计好的横向滚动行，不是溢出缺陷。

1. **Android 返回键在子页面会直接退出应用**（真机缺陷）。
   Capacitor 默认行为是任何页面按返回都退出。用户从行业列表点进详情再按返回，期望回列表，实际被踢出应用。
   新增 `src/utils/nativeBack.ts`：非首页回上一路由，首页才退出。仅原生平台注册。
   引入 `@capacitor/app` 8.1.1（官方小插件，`cap sync` 自动注册 `AppPlugin`）。
   实测：详情 → 返回 → 回列表（仍在应用内）；首页 → 返回 → 退出到桌面。
2. **补上 `docs/FLOW.md` 里无人认领的出口：行业详情 → 加入实验**。
   原先只有测评结果页和计划页能发起实验，行业详情看完就走到了死路。
   现在详情页底部有「用「XXX」开始一次 7 天实验」，直接创建实验并跳转详情。
   注意：FLOW 原文写的是「加进待实验清单」，这里**没有另建清单**，而是直接落成实验 ——
   所有路径都汇入实验，多一层清单只会多一个没人维护的中间态。
3. **15 题测评中途退出会丢失全部作答**（真实数据丢失风险）。
   返回手势很容易误触，一旦触发就要重填 15 题。现在作答与题号实时存 sessionStorage
   （`src/api/storage.ts` 新增 `readSession`/`writeSession`/`clearSession`），
   回到页面接着填，提交后清空。用会话级而非 localStorage：应用重启应给全新的一份。
   实测：答 3 题 → 离开 → 回来仍在第 4 题且前 3 题答案保留；提交后草稿清空、再进入是全新一份。
4. **`eslint.config.js` 漏配 `.vite/**`**（自测出的配置 bug）。
   `.vite` 是 dev server 的预打包缓存。只要「先 `pnpm dev` 再 `pnpm lint`」，就会报出
   425 个与项目代码无关的错误（来自 vue-router 的转译产物）。已加入 ignores。
5. **应用图标与启动页**。此前是 Capacitor 默认图标。
   新增 `tools/gen-icons.py`（Pillow）生成 26 个资源：各密度 `ic_launcher` /
   `ic_launcher_round` / `ic_launcher_foreground` 与横竖屏 `splash`。
   图形是一条基线上的向上箭头，表达「下一步」而不是「登顶」，符合 `docs/DESIGN.md` 的克制风格。
   自适应图标背景色由模板的 `#FFFFFF` 改为主色 `#2563EB`（前景是白色图形，白底会看不见）。
   `AppTheme.NoActionBarLaunch` 增加 `windowSplashScreenBackground=#FFFFFF`，与 drawable 启动页底色一致。
   实测：应用信息页显示新图标；冷启动显示白底 + 蓝色标记。
6. **版本号对齐**：`package.json` 与 `android/app/build.gradle` 统一到 `0.2.0` / `versionCode 2`
   （此前是 0.1.0 与 1.0 不一致）。
